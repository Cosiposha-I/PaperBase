# PaperBase — рабочая инструкция для сессии

Локальный поисковый движок по корпусу научных PDF (тема — биодизель, папка
`../Литература`). Этот файл — краткая шпаргалка; полная документация в
[README.md](README.md), готовый рецепт-навык — скилл `research-corpus-db`.

## Главный принцип

**Инструмент только ищет** и отдаёт фрагменты с источниками. **Синтез — на тебе
(Claude):** ответы, обзоры, таблицы Excel пишешь ты поверх вывода `search --json`.
Никаких платных API, ANTHROPIC_API_KEY не нужен.

## MCP: поиск прямо в разговоре (основной способ)

В Claude Desktop прописан MCP-сервер `paperbase` — **ищи корпус сам, инструментами**,
не проси пользователя гонять команды и вставлять вывод. Инструменты:

`paperbase_search` (по смыслу, top-K) · `paperbase_keyword` (по слову, все документы) ·
`paperbase_read` (страницы) · `paperbase_list` · `paperbase_bibliography` · `paperbase_stats`

Правила двух режимов и цитирования продублированы в описаниях инструментов.
Команды ниже остаются для случаев, когда MCP недоступен или нужен разовый прогон.

- Сервер: [mcp/server.py](mcp/server.py) — тонкий HTTP-клиент к `paperbase serve`,
  на голом stdlib (зависимостей не добавляет, `.venv` с CUDA-torch не трогает).
- Регистрация/снятие: `python mcp/register.py [--remove] [--dry-run]`.
- Проверка: `python mcp/test_server.py` (настоящий JSON-RPC-диалог, 20 проверок).
- **Прогрев.** Подъём `serve` с загрузкой bge-m3 — замерено 27 и 77 с (разброс большой).
  Сервер греет себя фоном при старте, поэтому первый поиск стоит ~78 мс вместо ~1,3 с,
  но сам подъём всё равно займёт своё. Перед работой, где важна скорость, поднимай
  `serve` заранее.

## Как запускать

- **GPU (по умолчанию для поиска/индексации)**: `.\pb-gpu.ps1 <команда>` — например
  `.\pb-gpu.ps1 search "запрос" --k 10 --json`. Обёртка использует venv с CUDA-torch.
- Обычный `python -m paperbase <команда>` идёт на CPU (годится для `list`/`stats`/`bib`).
- Windows PowerShell; рабочая папка — эта (`paperbase`). Модель эмбеддингов —
  `BAAI/bge-m3`; путь задаётся в `config.toml` (локальная папка — интернет не нужен,
  или имя HF-хаба — скачается автоматически).
- ⚠️ В `.venv` стоит CUDA-`torch` из локального колеса. **Не** запускай
  `pip install --upgrade` по requirements — перетрёт GPU-сборку на CPU. `torch` из
  `requirements.txt` намеренно убран; ставится отдельно (README, раздел GPU).

## Основные команды

```powershell
.\pb-gpu.ps1 search "смысловой запрос" --k 10 --json   # ПО СМЫСЛУ (top-K); RU→EN
python -m paperbase keyword "слово" --json             # ПО СЛОВУ: все документы со словом
python -m paperbase read <doc_id|файл> --pages A-B     # полный текст страниц
python -m paperbase list --json                        # перечень статей (id, cite_key, год)
python -m paperbase bib --out references.md            # список литературы
python -m paperbase stats                              # обзор корпуса
python -m paperbase check                              # здоровье базы
.\pb-gpu.ps1 serve --open                              # веб-интерфейс (или ярлык на рабочем столе)
```

Поиск идёт **по всему корпусу** — знать заранее файл не нужно. `--paper "<файл>"` —
необязательный фильтр (ограничиться одной статьёй). Для широких вопросов повышай `--k`.

Поле `--json`: `rank, score, doc_id, cite_key, citation, filename, title, year,
pages [start,end], section, text`.

## Правила синтеза (обязательны)

- **Всё на русском** (ответы, обзоры, значения в таблицах); единицы, DOI, латинские
  названия и прямые цитаты — как в оригинале.
- **Привязка к источнику**: каждое утверждение → `(Автор, Год)` + страница; fallback
  `[файл, стр. X]`. Ссылки бери из выдачи `search`/`bib`, не сочиняй.
- **Без выдумок**: чего нет во фрагментах — помечай «не найдено / не подтверждается
  корпусом». Сомневаешься — дочитай контекст через `read`.
- **Два режима.** Полнота («во всех ли статьях…», «перечисли все, где встречается X»)
  → `keyword` (точный список всех документов; язык важен: `phycocyanin` ≠ `фикоцианин`).
  Смысл → `search` с адекватным `k` и несколькими запросами. Семантический top-K НЕ
  перечисляет все документы — для полноты сначала `keyword`, потом синтез поверх него.

## Три рецепта (подробности — в README, раздел «Рабочие сценарии»)

1. **Вопрос-ответ**: `search "вопрос" --k 10 --json` → ответ со ссылками.
2. **Таблица → Excel**: по каждой статье `search --paper "<файл>" "поля"` / `read` →
   пишешь `.xlsx` через openpyxl (skill `xlsx`), одна строка на статью, пусто = «не найдено».
3. **Обзор**: `search "тема" --k 12 --json` (+ уточняющие) → `review.md` со ссылками и
   `bib` в конце.

Форматы корпуса: `.pdf` (+OCR для сканов), `.txt`, `.md`, `.rtf`.

## Добавление новых статей

Положить файл в папку `Литература` → `.\pb-gpu.ps1 ingest` (обработает только новые).
`ingest --prune` убирает записи удалённых файлов. Бэкап делается автоматически.

## Несколько тем (мультикорпус)

Одна установка обслуживает много тем; у каждой своя папка и свой `data_dir`. Ярлык
«PaperBase» открывает меню (`paperbase menu`) — выбор/добавление тем из `corpora.json`.
В коде тему задают `--config` или env `PAPERBASE_CORPUS_DIR`/`PAPERBASE_DATA_DIR`.
Биодизель — `data/`, остальные — `data-<тема>/`.

## Важные нюансы (для сессии, что правит код)

- **Векторный индекс на ASCII-пути.** Путь проекта содержит кириллицу («Биодизель»),
  а ChromaDB 1.5.9 не читает HNSW-сегмент по не-ASCII пути. Поэтому `config.chroma_dir`
  переносит индекс в `%LOCALAPPDATA%\PaperBase\chroma-<хэш>`. SQLite/логи/бэкапы — в
  `data_dir` как есть. Индекс восстановим из SQLite: `reindex`.
- **Регистр в поиске по слову.** Встроенная в SQLite `lower()` понижает только
  латиницу: `lower('Андрюса')` возвращает строку без изменений. Из-за этого `keyword`
  не находил имена собственные («Андрюс», «Блэкман», «Иерусалимский» → 0 документов
  при трёх реальных). Исправлено: `Store` регистрирует свою `ulower()` на Python.
  Регрессия закрыта `tests/test_keyword_unicode.py` — **не заменять `ulower` обратно**.
- **OCR смешивает кириллицу с латиницей (не исправлено).** В корпусах со сканами до
  61% фрагментов содержат слова вроде `KOHцентрация`, `микроорганизMOB`, `BOдород` —
  латинские двойники букв. Смысловой поиск это переживает (bge-m3 устойчив), а
  `keyword` такие слова не найдёт. Если поиск по слову даёт подозрительный ноль —
  перепроверь смысловым поиском, прежде чем считать тему непокрытой.
- **OCR — только CPU, но параллельно.** Tesseract не умеет GPU; сканы распознаются
  страницами в пуле потоков (`[ocr] workers`, 0 = ядра − 2, ≤16; `OMP_THREAD_LIMIT=1`).
  Замер на книжном скане (32 стр., Ryzen 9 8940HX, 16 ядер): 0,81 с/стр в 16 потоков
  против 3,08 с/стр в один, текст совпадает побайтно. Потолок ~5–6× задаёт сам
  Tesseract на этом железе: «голые» 16 процессов без нашего кода дают те же 0,57 с/стр,
  рендер страницы (0,08 с) и замок вокруг PyMuPDF узким местом не являются.
  GPU при ingest занят только на этапе эмбеддингов — это нормально. EasyOCR (GPU)
  хуже на русском книжном тексте.
- **Лаунчеры (`*.cmd`) — только ASCII + CRLF** (cmd.exe ломается на кириллице в UTF-8).
- **Не** делать `pip install --upgrade` по requirements — перетрёт CUDA-torch.

## Если что-то не так

`python -m paperbase check` (окружение + целостность SQLite↔ChromaDB) и
`check --errors`. Восстановление — `restore --yes`; пересборка векторов без PDF —
`.\pb-gpu.ps1 reindex`.
