# PaperBase — локальный поиск по корпусу научных PDF

Локальная система для работы с корпусом статей (тема — биодизель, но корпус любой):
семантический поиск с точной привязкой «статья + страница», извлечение текста,
метаданные и список литературы. **Без единого платного API и без LLM внутри** —
инструмент только ищет и отдаёт фрагменты с источниками; синтез ответов, обзоры
и таблицы Excel делает Claude в разделе «Код» Claude Desktop поверх вывода `--json`.

## Архитектура

```
PDF (Литература/) ──ingest──> SQLite (документы, чанки) + ChromaDB (векторы)
                                        │
запрос ──search──> локальные эмбеддинги (BAAI/bge-m3) ──> топ-K чанков
                                        │            с cite_key, файлом, страницами
Claude («мозг») читает --json ──> ответ / обзор / .xlsx со ссылками (Автор, Год, стр.)
```

- **Эмбеддинги**: `BAAI/bge-m3` — локально, мультиязычно, кросс-язычно (русский
  запрос находит фрагменты в английских статьях). Контекст 8192 токена (против 512
  у e5), поэтому чанк крупнее — см. раздел «Размер чанка и модель» ниже. Fallback
  для слабых машин: `paraphrase-multilingual-MiniLM-L12-v2` (см. `config.toml`).
- **Хранение**: SQLite (`data/corpus.db`) + ChromaDB (`data/chroma/`).
- **Форматы**: `.pdf` (PyMuPDF; сканы без текстового слоя — OCR через Tesseract),
  а также `.txt`, `.md` и `.rtf` (читаются напрямую, RTF — best-effort). Список —
  `extract.SUPPORTED_EXTS`. У текстовых файлов номера страниц условны (псевдо-пагинация).

## Установка

Всё уже работает на глобальном Python этой машины (3.12, зависимости установлены).
Для чистой установки на другой машине:

```powershell
cd paperbase
python -m venv .venv
.venv\Scripts\activate
# ВАЖНО: сначала поставить нужную сборку torch, потом остальное.
# GPU (эта машина): pip install "D:\Programms\torch-2.11.0+cu128-cp312-cp312-win_amd64.whl"
# или CPU:          pip install torch
pip install -r requirements.txt        # torch здесь НЕ указан — не перетирает GPU-сборку
```

> `torch` намеренно убран из `requirements.txt`, чтобы `pip install -r` (или его
> `--upgrade`) не заменил CUDA-сборку на CPU. Ставьте torch первым — тогда
> `sentence-transformers` увидит его и не подтянет CPU-версию. Dev-тесты:
> `pip install -r requirements-dev.txt` (pytest).

**Модель эмбеддингов** `BAAI/bge-m3` (~2.3 ГБ). На этой машине она скачана вручную
в локальную папку `D:\Models\bge-m3`, и путь прописан в `config.toml`
(`[embedding] model = "D:/Models/bge-m3"`) — интернет для работы не нужен. Для чистой
установки на другой машине укажите `model = "BAAI/bge-m3"`, и модель скачается
автоматически в кэш HuggingFace (`~/.cache/huggingface`) при первом запуске.

### Tesseract OCR (для сканов) — установлен

На этой машине **Tesseract 5.5.0 установлен** в `D:\Programms\Tesseract-OCR`, языки
`eng` и `rus` присутствуют. Путь прописан в `config.toml`:

```toml
[ocr]
languages = "eng+rus"
tesseract_cmd = "D:/Programms/Tesseract-OCR/tesseract.exe"
```

`python -m paperbase check` показывает строку `tesseract  доступен`. Страницы без
текстового слоя теперь распознаются, а не пропускаются. Если переустановите
Tesseract в другое место — поправьте `tesseract_cmd` (или оставьте пустым, если
бинарник попал в PATH).

### GPU (уже настроено)

Глобальный torch — CPU-сборка. Чтобы не трогать глобальный ML-стек (Whisper, ASR,
ComfyUI), CUDA-ускорение вынесено в **изолированный venv** `paperbase\.venv`:
он создан с `--system-site-packages` (наследует все зависимости paperbase из
глобального Python), а внутрь поставлен только `torch 2.11.0+cu128` из локального
wheel — он перекрывает CPU-torch **только для paperbase**. Глобальное окружение не
изменено.

Как это было сделано (повторять не нужно, уже готово):

```powershell
python -m venv --system-site-packages .venv
.\.venv\Scripts\python.exe -m pip install --force-reinstall --no-deps `
  "D:\Programms\torch-2.11.0+cu128-cp312-cp312-win_amd64.whl"
```

Запуск на GPU — через обёртку `pb-gpu.ps1` (подставляет python из venv):

```powershell
.\pb-gpu.ps1 ingest
.\pb-gpu.ps1 search "выход FAME" --k 8 --json
```

`device = "auto"` в `config.toml` сам выбирает CUDA, когда видит её (проверено:
`torch.cuda.is_available() = True`, RTX 5070 Ti). Замер: ~456 чанков/с на GPU
против единиц чанков/с на CPU — эмбеддинги ускоряются в десятки раз.

**Где именно выигрыш:** GPU ускоряет **`ingest`** (пакетные эмбеддинги сотен
чанков). Для одиночного `search` в CLI основное время — загрузка модели при каждом
запуске (~20–30 с холодного старта). **Веб-интерфейс `serve` эту проблему снимает:**
модель грузится один раз при старте сервера и остаётся тёплой, поэтому каждый
последующий поиск — доли секунды. Для больших батчей и переиндексации — `pb-gpu.ps1`.
Для быстрых команд без модели (`list`, `stats`, `bib`, `read`) устройство роли не играет.

## Команды

```powershell
cd C:\Users\ASUS\Desktop\Биодизель\paperbase

# Индексация (папка по умолчанию — из config.toml; идемпотентно по sha256)
python -m paperbase ingest                         # добавит только новые PDF
python -m paperbase ingest --prune                 # + убрать записи удалённых файлов
python -m paperbase ingest "D:\другая\папка" --reingest --no-crossref

# Пересборка векторов из SQLite (без чтения PDF/CrossRef) — после смены модели
# эмбеддингов или для восстановления индекса. Быстрее полного --reingest.
.\pb-gpu.ps1 reindex

# Поиск ПО СМЫСЛУ (семантический; ядро; --json — для машинного чтения).
# Возвращает top-K релевантных фрагментов. --paper НЕОБЯЗАТЕЛЕН (см. ниже).
python -m paperbase search "катализаторы переэтерификации выход FAME" --k 8
python -m paperbase search "feedstock oils" --k 12 --year-min 2022 --paper "*Review*" --json

# Поиск ПО СЛОВУ (keyword; модель не нужна; список ВСЕХ документов со словом).
# Для вопросов «в каких статьях есть слово X». Слово точное: phycocyanin ≠ фикоцианин.
python -m paperbase keyword "phycocyanin"
python -m paperbase keyword "переэтерификация" --paper "*Review*" --json

# Полный текст статьи (перечитывает PDF)
python -m paperbase read 3 --pages 4-6
python -m paperbase read "mixed oils" --json

# Список литературы (метаданные best-effort — правьте вручную при необходимости)
python -m paperbase bib --out references.md
python -m paperbase bib --keys "Brahma2022,Zheng2025" --json

# Обзор корпуса
python -m paperbase list
python -m paperbase stats --json

# Диагностика (окружение, конфиг, целостность SQLite ↔ ChromaDB, журнал ошибок)
python -m paperbase check
python -m paperbase check --deep      # + проверка загрузки модели эмбеддингов
python -m paperbase check --errors    # показать последние ошибки/предупреждения

# Резервные копии базы
python -m paperbase backup            # полная копия (SQLite + векторы)
python -m paperbase backup --db-only  # компактная копия без векторов (для большого корпуса)
python -m paperbase backup --list     # список копий
python -m paperbase restore --yes     # восстановить из последней копии
python -m paperbase restore paperbase-20260710-210745.zip --yes
# после restore db-only копии — пересобрать поиск: python -m paperbase reindex

# Веб-интерфейс (браузер, модель тёплая — поиск быстрый)
.\pb-gpu.ps1 serve --open             # запуск на GPU + открыть браузер
python -m paperbase serve --port 8765 # без GPU-обёртки
# ярлык «PaperBase» на рабочем столе делает то же в один клик
```

Формат выдачи `search` (человекочитаемый):

```
#1  score=0.665  [Brahma2022] Brahma et al., 2022 — Biodiesel production from mixed oils 2022.pdf, стр. 4–5 (Results)
<текст фрагмента>
```

В `--json`: `rank, score, doc_id, cite_key, citation, filename, title, year,
pages [start, end], section, text`.

## Веб-интерфейс (`serve`)

Удобный «читальный зал» корпуса в браузере — для повседневного поиска руками,
без набора команд. Запуск:

```powershell
.\pb-gpu.ps1 serve --open        # на GPU, откроет http://127.0.0.1:8765
```

Что умеет:

- **Два режима поиска** (переключатель «режим»): **по смыслу** (семантика, top-K,
  фильтры k/год/файл) и **по слову** (keyword — список всех документов со словом,
  с числом фрагментов и примером).
- **Результаты со ссылками**: `(Автор, Год) · [cite_key] файл, стр. X · раздел` и
  близость в %. Полный текст фрагмента.
- **Просмотр источника**: клик «Открыть источник» показывает текст страницы **и её
  изображение из PDF** рядом — визуальная проверка привязки к странице; листание
  ◀/▶ и стрелками.
- **Копировать для Claude**: кладёт фрагмент (JSON: cite_key, citation, страницы,
  текст) в буфер — вставляете в чат, и Claude синтезирует ответ уже с готовой ссылкой.
- **Боковая панель**: статистика корпуса, список статей (клик → чтение), кнопка
  «Скачать список литературы», индикатор здоровья базы (данные из `check`).

Важно: интерфейс **только ищет и показывает**. Ответы, обзоры и таблицы Excel
по-прежнему пишет Claude в чате — принцип «инструмент = поиск, без платного LLM»
сохранён. Сервер локальный (по умолчанию только `127.0.0.1`), наружу не смотрит.

## Два режима поиска: по смыслу и по слову

| | **search** (по смыслу) | **keyword** (по слову) |
|---|---|---|
| Что делает | семантический поиск, top-K близких фрагментов | все документы, где встречается слово |
| Язык | кросс-язычный (рус. запрос → англ. фрагменты) | точное совпадение: `phycocyanin` ≠ `фикоцианин` |
| Модель | нужна (эмбеддинги) | не нужна (быстро, SQL по тексту) |
| Отвечает на | «что говорят про X», «сравни подходы» | «в каких статьях есть слово X», «сколько их» |
| Полнота | НЕ гарантирует все документы (это top-K) | перечисляет все + счётчик |

**Правило синтеза (важно):** для вопросов на **полноту** («во всех ли статьях…»,
«перечисли все, где…») сначала бери точный список через `keyword`, и уже поверх него
синтезируй — семантический top-K тут недосчитает. Для **смысловых** вопросов —
`search` с адекватным `k` (для обзора 12–40) и **несколькими** запросами (разные
формулировки, RU+EN, подтемы), затем объединяй. `k` выбирается под задачу; дефолт 8 —
для узкого факта, не для «перечисли всё».

## Размер чанка и модель эмбеддингов

Частый вопрос: «почему не увеличить число токенов в чанке, чтобы было больше
контекста?» У прежней модели `e5-large` жёсткий лимит **512 токенов** — чанк
крупнее молча обрезался при кодировании, и хвост выпадал из поиска. Поэтому корпус
переведён на **`BAAI/bge-m3`** (контекст 8192), а чанк поднят до **800 токенов**
(`config.toml → [chunking]`).

Почему 800, а не максимум: слишком крупный чанк расширяет диапазон страниц в ссылке
(`стр. 12–15` вместо `стр. 13`) и «размывает» вектор (один вектор усредняет
несколько подтем) — падает точность и привязки, и ранжирования. 800 — компромисс.
При этом **полный текст чанка всегда хранится и возвращается**, а `read` отдаёт
целые страницы: для анализа (его делает Claude) контекст не ограничен размером чанка.

Вернуться на лёгкую модель можно в `config.toml` (`model =
"sentence-transformers/paraphrase-multilingual-MiniLM-L12-v2"`, `chunk_tokens = 380`)
+ `ingest --reingest`. Любая смена модели требует полной переиндексации.

## Рост корпуса и поиск «не знаю, в каком файле»

Система рассчитана на рост числа статей (сотни и более) без переделок.

**Поиск не требует знать файл.** Обычный `search "вопрос"` (без `--paper`) ищет по
смыслу **сразу по всему корпусу** и возвращает самые релевантные фрагменты с
указанием файла и страницы — не нужно помнить названия статей, годы или где что
лежит. Задаёте вопрос своими словами (хоть по-русски) — находятся нужные куски даже
при другой формулировке или языке. Фильтр `--paper` — **необязательный**, только для
случая «ограничиться конкретной статьёй» (напр. выгрузка в Excel по одной статье).
Для широких вопросов увеличивайте `k` (в вебе — поле «фрагментов (K)»).

**Что обеспечивает масштабируемость:**

- **Инкрементальная загрузка**: `ingest` пропускает уже загруженные файлы (по sha256),
  добавляются только новые PDF. `--prune` убирает из базы записи удалённых файлов;
  при совпадении DOI выводится предупреждение о возможном дубликате.
- **Векторный поиск** на ChromaDB (HNSW) — сотни тысяч фрагментов, отклик за доли
  секунды. Фильтры по файлу/году проталкиваются прямо в запрос, поэтому надёжны и на
  большом корпусе.
- **`reindex`** пересобирает векторы из текста в SQLite (без чтения PDF и CrossRef) —
  быстрая смена модели эмбеддингов и восстановление индекса.
- **`backup --db-only`** — компактные копии (SQLite ~единицы МБ вместо десятков);
  векторы восстанавливаются через `reindex`.
- **Массовая первая загрузка**: CrossRef обращается к сети по каждому DOI (таймаут 5 с).
  Для сотен новых файлов сразу удобнее `ingest --no-crossref` (быстро), а метаданные
  обогатить позже отдельным прогоном `ingest --reingest` уже с CrossRef.

## Несколько тем (мультикорпус) и ярлык-меню

Одна установка (код + venv + модель bge-m3) обслуживает **сколько угодно тем** —
пересобирать программу не нужно. У каждой темы своя папка со статьями и свой индекс
(`data_dir`), базы не пересекаются.

**Ярлык «PaperBase» на рабочем столе открывает меню** (`paperbase menu`): список
сохранённых тем, выбор любой — запуск её веб-интерфейса; пункт «Добавить новую тему»
спрашивает папку и название, сохраняет в реестр и строит базу. Гибко к смене пути.

Реестр тем — `corpora.json` в корне проекта (правится и вручную):

```json
[
  { "name": "Биодизель", "corpus": "…/Литература", "data": "data", "port": 8765 },
  { "name": "Работа",    "corpus": "…/Актуальный список", "data": "data-rabota", "port": 8770 }
]
```

- `data` — папка индекса (относительно проекта); у каждой темы своя, поэтому базы
  независимы. `port` — на каком порту открывать веб-интерфейс этой темы.
- Первый запуск темы сам строит базу (индексация разовая), дальше — сразу поиск.

**Для командной строки** то же доступно двумя способами:

```powershell
# отдельный полный конфиг темы
.\pb-gpu.ps1 --config C:\path\config-тема.toml search "запрос" --json

# или переопределить только пути (как делает меню)
$env:PAPERBASE_CORPUS_DIR = "C:\путь\к\папке"
$env:PAPERBASE_DATA_DIR    = "data-тема"
.\pb-gpu.ps1 ingest ; .\pb-gpu.ps1 serve --open --port 8770
```

`config.toml` при этом даёт общие настройки (модель, OCR, бэкапы), а `corpus_dir`/
`data_dir` берутся из темы. Базовая тема (Биодизель, `data/`) не затрагивается.

## Рабочие сценарии (выполняет Claude в разделе «Код»)

Инструмент даёт поиск — синтез делает Claude. Правила для всех сценариев:

- **Всё на русском**: ответы, обзоры, значения в таблицах — на русском, независимо
  от языка статьи. Единицы измерения, DOI, латинские названия и прямые цитаты —
  как в оригинале.
- **Привязка к источнику**: каждое утверждение — со ссылкой `(Автор, Год)` и
  страницей; fallback `[filename, стр. X]`.
- **Никаких выдумок**: что не подтверждено найденными фрагментами — явно помечать
  «не найдено» / «не подтверждается корпусом».
- **Полнота → keyword**: на вопросы «во всех ли статьях…», «перечисли все, где есть X»
  сначала бери точный список `keyword "X"`, затем синтезируй; семантический top-K тут
  недосчитает (см. «Два режима поиска»).

### 1. Вопрос-ответ

```
python -m paperbase search "как температура влияет на выход биодизеля" --k 10 --json
```

Claude читает JSON, синтезирует ответ на русском; каждое утверждение подкреплено
конкретным фрагментом: `…выход растёт с повышением температуры (Brahma et al., 2022, стр. 5)…`.
При сомнении — `read <doc_id> --pages A-B` для контекста вокруг фрагмента.

### 2. Таблица данных → Excel

Для каждой статьи (`list --json` даёт перечень) Claude выполняет точечные
`search --paper "<файл>" "катализатор мольное соотношение выход"` и/или `read`,
извлекает поля (сырьё, катализатор, тип катализа, спирт:масло, T °C, время,
выход FAME %, цетановое число, вязкость, плотность, T вспышки, стандарт),
затем сам пишет `.xlsx` через openpyxl: одна строка на статью, с `cite_key` и
годом; отсутствующее — «не найдено». Большой корпус — батчами по 10–20 статей.

### 3. Обзор по теме

```
python -m paperbase search "тема обзора" --k 12 --json   # + 2–3 уточняющих запроса
python -m paperbase bib --out references.md
```

Claude пишет `review.md`: группировка по подтемам, каждое утверждение со ссылкой
`(Автор, Год)`, в конце — список литературы из `bib`.

## Хранение данных

- `data/corpus.db` — SQLite: `documents` (filename, sha256, cite_key, title,
  authors, year, journal, doi, abstract, num_pages, status), `chunks` (text,
  page_start, page_end, section).
- **Векторный индекс ChromaDB**: обычно `data/chroma/`, НО если путь проекта содержит
  не-ASCII символы (у нас — «Биодизель»), индекс переносится на ASCII-путь
  `%LOCALAPPDATA%\PaperBase\chroma-<хэш>` (по хэшу data_dir, у каждой темы свой).
  Причина — баг ChromaDB 1.5.9: бинарный HNSW-сегмент по пути с кириллицей на Windows
  не читается после перезапуска. Логика — `config.chroma_dir`; индекс восстановим
  из текста в SQLite командой `reindex`. В metadata вектора: doc_id, cite_key,
  filename, year, page_start, page_end, section.
- `data/logs/ingest.log` — техжурнал по файлам (конвейер не падает из-за одного PDF).
- `data/logs/errors.log` — **место, куда смотреть, если что-то пошло не так**:
  человекочитаемо, с трейсбеками, помечено по этапам и сессиям.
- `data/logs/diagnostics.jsonl` — то же структурированно (по записи на проблему),
  для машинного разбора и команды `check`.
- `data/backups/paperbase-*.zip` — резервные копии (SQLite + ChromaDB + config).

Полный сброс индекса: удалить папку `data/` и запустить `ingest` заново.

## Проверки на каждом этапе и где читать ошибки

Конвейер `ingest` не «глотает» проблемы — после каждого этапа работает валидатор
(в коде — `checks.validate_*`), а результат пишется в единый журнал. Ни одна
проверка не роняет процесс: файл со сбоем логируется, обработка продолжается.

| Этап | Что проверяется |
|------|-----------------|
| extract | есть ли текстовый слой; сколько страниц ушло/не ушло в OCR |
| chunk   | получены ли чанки; не длиннее ли они лимита модели (иначе усечение) |
| embed   | число векторов = числу чанков; постоянная размерность; нет NaN/inf |
| store   | записалось ли в SQLite столько же, сколько в ChromaDB (нет рассинхрона) |

Всё найденное стекается в **два файла** (это и есть «отдельное место, где спокойно
прочитать ошибки»):

- `data/logs/errors.log` — читать глазами;
- `data/logs/diagnostics.jsonl` — парсить.

Быстрый обзор без открывания файлов:

```powershell
python -m paperbase check            # окружение + целостность + сводка по журналу
python -m paperbase check --errors   # последние строки errors.log
python -m paperbase check --json     # всё машиночитаемо
```

`check` также ловит проблемы вне ingest: рассинхрон SQLite ↔ ChromaDB (после сбоя
или ручного вмешательства), пропавшие с диска PDF, документы без чанков или со
статусом ≠ `ok`, отсутствие Tesseract, несоответствие `chunk_tokens` лимиту модели.

## Резервные копии

База (SQLite + векторы ChromaDB + `config.toml`) архивируется в один `.zip`:

- **автоматически** перед каждым `ingest` — но не чаще, чем раз в
  `min_interval_hours` (по умолчанию 12 ч), чтобы не плодить копии;
- **вручную**: `python -m paperbase backup`.

Хранятся последние `keep` копий (по умолчанию 10, старые удаляются). Восстановление —
`python -m paperbase restore [имя] --yes`; перед перезаписью текущее состояние само
уходит в страховочную копию.

**Почему такой интервал.** Корпус меняется только во время `ingest`, поэтому копия
привязана именно к нему — это защищает рабочее состояние в нужный момент, а не по
случайному таймеру. Настройки — секция `[backup]` в `config.toml`.

Перед `ingest --reingest` (полная перезапись базы) бэкап делается **всегда**, минуя
throttle: операция деструктивная. `--reingest` к тому же пересоздаёт векторную
коллекцию ChromaDB с нуля (чистые `add`), а в конце `ingest` работает финальный
гейт: если векторный индекс не читается или разошёлся с SQLite — в журнал пишется
явная ошибка с советом `restore`.

Если хотите копию строго по расписанию (например, раз в неделю), добавьте задачу
Планировщика Windows:

```powershell
schtasks /Create /SC WEEKLY /D SUN /TN "PaperBase Backup" /ST 20:00 ^
  /TR "cmd /c cd /d C:\Users\ASUS\Desktop\Биодизель\paperbase && python -m paperbase backup"
```

## Принятые допущения

1. **Чанк 800 токенов, overlap 150** на модели `BAAI/bge-m3` (контекст 8192).
   Ранее было 450 на e5-large из-за лимита 512 — см. раздел «Размер чанка и модель».
   Настраивается в `config.toml`.
2. **venv только для GPU-torch**: основные зависимости стоят глобально, а в
   `paperbase\.venv` (создан с `--system-site-packages`) добавлен лишь CUDA-torch —
   поэтому GPU-команды идут через `pb-gpu.ps1` (см. раздел GPU). Обычный
   `python -m paperbase …` работает на глобальном Python (CPU).
3. **OCR деградирует мягко**: без Tesseract сканы пропускаются с предупреждением,
   а не роняют конвейер.
4. **Переносы слов склеиваются** не только по дефису, но и по мягкому переносу
   (U+00AD) и по `@`: часть PDF (напр. Дамаскин «Электрохимия») кодирует символ
   переноса шрифтом как `@`, из-за чего слова оставались разорванными
   («вос@произведение») — это ломало и вид, и поиск по слову. Одиночный `@` между
   кириллическими буквами тоже считается подменённым дефисом; латиница вокруг `@`
   (почта) не трогается. Логика — `extract._clean_block`.
4. **CrossRef — только по DOI** (без поиска по названию), чтобы не притянуть чужие
   метаданные; таймаут 5 с, офлайн просто пропускается (`--no-crossref` отключает).
5. **cite_key** = `ФамилияПервогоАвтораГод` (напр. `Sharma2022`), при коллизии —
   суффикс `a/b/…`; без автора — первое значимое слово названия + год.
6. **Год без метаданных** берётся из имени файла (если там есть), иначе максимальный
   правдоподобный год с первых двух страниц. Метаданные best-effort — для чистового
   списка литературы сверяйте `references.md` с PDF.
7. Раздел статьи (`section`) определяется эвристикой по заголовкам (EN/RU) и может
   быть пустым — на точность привязки к странице это не влияет.
